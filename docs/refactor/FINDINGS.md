# Findings register

Bugs, surprises and strange design decisions found in the code, tests or build while working through the plan. `PROGRESS.md` says what each chunk did; this file keeps the issues themselves in one place, so they are not lost in old log entries.

Rules (also in `PLAN.md` § Session protocol):
- Add an entry when you find something, even if it is out of scope for the chunk. Give it the next free ID; never reuse IDs.
- Kinds: **bug** (wrong behaviour), **surprise** (correct but unexpected, and likely to trip someone up), **design** (a strange or questionable decision worth revisiting).
- Don't fix a finding that changes observable output (stdout, stderr, outputs, exit codes) inside a refactor chunk. Record it, and ask the user before fixing it in its own commit.
- When an entry is fixed or settled, move it to § Closed with the commit or chunk.

## Open

- **F1** (bug, found C2): `--progress` prints one `\r N%` line per step instead of one per percent. `print_progress` takes `last_percent` by value, so the caller's copy never changes (`model/Simulation.cpp`). Fixing it changes stderr only. Planned for M3 if the user agrees.
- **F2** (bug, found S1): after any caught exception, `main()` calls `perror("OpenMalaria")` whenever `errno != 0` (`model/main.cpp:119`). `errno` is often left over from an earlier, harmless failed file lookup, so error reports end with an unrelated `OpenMalaria: No such file or directory`. Changes stderr; candidate for M3 or I2.
- **F3** (surprise, found S1): invalid input can be reported as a C++ bug. `popSize="-5"` in `scenario1` gives `Code error: initialKappa is invalid … This is likely an error in the C++ code. Please report!` (from `NonVectorModel.h:107`), with exit 75, instead of an input-validation error. Scenario values aren't checked before they reach model code. Relevant to E (config boundary validation).
- **F4** (bug, found S1): `test/run.py` `findFile` returns from inside its loop, so it gives an arbitrary existing candidate from a `set`, not the newest as intended. Harmless while only one `openMalaria` exists in the build dir.
- **F5** (bug, found S1): `test/run.py` prints "No output 'output.txt'; error messages:" and then reads `stderr.txt` but throws the content away (`se.read()` is never printed). openMalaria doesn't write `stderr.txt` anyway, so the branch is dead.
- **F6** (design, found S1): `test/run.py` replaces `sys.path[0]` with `util/` at import time, so any script that imports it loses its own directory from the import path. `run_replicates.py` restores `sys.path` around the import.
- **F7** (surprise, found S1): binary survey output decoded by `binaryToText` lists all integer measures before the double ones. The rows match text output only when matched by (survey, group, measure), not line by line. `compareOutput.py` matches by key, so ctest's `--binary` mode is unaffected.
- **F8** (surprise, found A2): 6 of the 57 `test/scenario*.xml` files are not registered in `test/CMakeLists.txt` (2, 3, IPT, VT, MultiVecPopInterventions, VecLC*), some disabled for unknown reasons ("TODO: since when?"). They are not covered by any gate.
- **F9** (surprise, found B4): 4 CxxTest suites (AnophelesModel, DescriptiveInfection, ESCaseManagement, MosqLifeCycle) are not compiled, so renames and refactors can't reach them and they may have rotted. M9 ports or deletes them. **D3:** DescriptiveInfection has rotted: its `setUp` calls `UnittestUtil::Infection_init`, `DescriptiveInfection::initParameters` and a `gsl` namespace, none of which exist, so clang-tidy can't parse it. D3 renamed `UnittestUtil::DescriptiveInfection_init` and left the suite's call to the old name. AnophelesModelSuite likewise still calls `CommandLine::lookupResource` (now `lookup_resource`).
- **F10** (surprise, found M0): GSL is GPL-3.0-or-later and Xerces-C is Apache-2.0, so a distributed `openMalaria` binary is effectively GPLv3-only already, although the project says GPL-2.0-or-later. Bears on Decision 6.
- **F11** (surprise, found M0): `contrib/README.txt` is stale (CxxTest 3.10.1 under LGPL-2.1; the tree has 4.4 under LGPL-3.0). `DEPENDENCIES.md` is the source of truth.
- **F12** (surprise, found M0): `docker/Dockerfile` uses Ubuntu 22.04's CMake 3.22, below the new 3.24 minimum. It builds upstream's `schema-50` branch, so it is unaffected for now.
- **F13** (design, found M1): the `OM_CXXTEST_ENABLE` option now also enables the Catch2 tests. Rename it in M9.
- **F14** (design, found C2): stdout uses `std::endl` (flush on every line) in many places, and changing it would change the interleaving of stdout and stderr. It is kept with `NOLINT(performance-avoid-endl)` until M3 moves console output to spdlog.
- **F17** (surprise, found S2): leave-one-out miss counts are heavy-tailed when cells are strongly correlated. ModelNameNoOverrides (N = 38, 67k non-zero-width cells): median 480 misses, mean 2127, max 11278, so the 99.9% threshold is about the maximum and a whole-run shift of up to ~11k missed cells would pass. scenario1 (N = 50, 838 non-zero-width cells): median 46, max 99. S6's power study should show whether the aggregates or a per-measure test are needed to catch such shifts. **S6:** confirmed. In the power study the power comes from the aggregates; e.g. Genotypes at 5% higher force of infection fails 98% of runs on aggregates while its miss count stays unremarkable (p ≈ 0.2). See F31.
- **F20** (surprise, found S3): with fewer than 99 replicates, rule (a) can never fail, because the smallest possible p is 1/(N + 1) > 1%. The generator warns and writes `max_passing_misses: unlimited`. Use N ≥ 100; S5 plans 500.
- **F22** (design, found S5): `run_replicates.py` records `commit` and `dirty` in `meta.json` from the source tree's state when each scenario starts, not from the source the binary was built from. Editing or committing tracked files while a long job runs changes what is recorded, even though the binary is the same. Only `binary_sha256` really identifies the build. In S5, scenario 12 was recorded as `dirty: true` because uncommitted Python edits were in the tree. Fix candidate: have CMake stamp the commit and dirty flag into the build dir at build time, and read that. Hit again in S6: scenario1's remade replicates were recorded `dirty: true` (uncommitted references and a new script in the tree), so they were remade once more from a clean tree.
- **F25** (surprise, found S5): `run_replicates.py` checks that an existing `OUT` dir was made by the same binary before it looks for finished seeds. A complete dir from an equivalent but differently-hashed build (e.g. another build dir of the same commit) is refused with exit 2, even though there is nothing left to run. Harmless, but a driver that loops over scenarios logs errors for them. Skipping the hash check when every requested seed is already present would fix it.
- **F30** (design, found D2): the unit tests' `Human`s seed their RNGs from one process-wide master RNG (`UnittestUtil::createHuman`; before D2 the never-seeded global `master_RNG`). Each test's draws therefore depend on how many humans earlier tests created, so the CxxTest results depend on test order and on adding or removing a test. D2 kept this as is, to keep G-unit identical. Candidate fix (M9, when the suites move to Catch2): bind a fresh `MasterRng(0, 0)` per test, and re-derive any expected values that change.
- **F32** (surprise, found S7): EffectiveDrug's outputs are heavy-tailed. A few replicates have an outbreak (clinical episodes up to 2081 against a mean of 50; skew about 10 in the episode, treatment and death totals), so the K-run mean of those quantities is dominated by whether a group holds an outbreak replicate. Its group-test threshold is 17.4 (others 3.9–7.5), and the group test detects neither a 20% higher force of infection (largest shift −0.1 SD anyway) nor much else short of the intervention removal. A Wilcoxon rank-sum group statistic, calibrated the same way, was compared on the S6 runs: no better for EffectiveDrug, and overall equal (≥ 80% power at FOI × 1.2 in 23 scenarios against the mean test's 24), so the plan's mean test was kept. Whether the outbreaks are realistic model behaviour or a sign of something odd in the scenario was not looked at.
- **F33** (surprise, found S7): the group test's leave-K-out calibration is slightly conservative on fresh runs. Of 438 disjoint fresh groups, 15 exceed the 5% quantile (21.9 expected) and 1 the 1% quantile (4.4 expected), each about 1.5–1.9 SD low. The cause is not established. A candidate: calibration standardises each resample by the SD of the other N − K replicates, which varies with which outliers fall in the group and so widens the tail, while the check uses the fixed SD of all N. It errs towards fewer false alarms, so it was left as is.
- **F34** (surprise, found V1): `test/expected/ctsoutGenotypes.txt` is stale. Genotypes writes no ctsout, and `run.py` compares a ctsout only when the run writes one, so the file is never checked and V1 left it as it was. Candidate: delete it, and have `run.py` fail when an expected ctsout exists but the run wrote none.
- **F39** (design, found M4): some CxxTest suites pin exact values that come from random draws: `EmpiricalInfectionSuite` (seven densities, `TS_ASSERT_APPROX`) and the `MolineauxStats{Orig,Pairwise}RG` quantile files (tolerance 1e-4, compared by `MolineauxInfectionSuite`'s `compare`). Any change to a sampler or to draw order breaks them, and re-pinning them, as M4 did (0cbf0d72), checks nothing about the model. The normal-only `MolineauxStats{Orig,Pairwise}` files are pinned the same way. Candidate for M9 (port to Catch2): test properties the model must have (e.g. the 1/10 density relation `testUpdatedReducedInf` already notes, or quantiles against wide bounds), or keep the pins but generate them with the suite's `write()` in a documented step. Related to F30.
- **F41** (bug, found D3): `--validate-only`, `--print-model` (`-m`), `--print-EIR`, `--print-interventions`, `--print-survey-times`, `--print-genotypes` and `--sample-interpolations` set `CommandLine::SKIP_SIMULATION`, but nothing has read that flag since upstream #296 (82872744, "Refactor main loop"), which dropped the `if (!SKIP_SIMULATION)` around the run. So each of them prints what it should and then runs the whole simulation, writing `output.txt` and `ctsout.txt` (checked in D3: `scenario1.xml --validate-only` writes both). `--help` says they validate or print "and exit". Fixing it changes outputs and exit timing; candidate for I2 (CLI subcommands), or earlier if the user wants.
- **F42** (bug, found D3): the `OM_STREAM_VALIDATOR=ON` build doesn't compile at 389ee2e9: `StreamValidator.h:91` (`no matching function for call to 'toSVType'`) and template syntax errors in `StreamValidator.cpp` around lines 53–62. The feature has rotted and no gate builds it. Since D3, `CommandLine::parse` also calls `StreamValidator.loadStream`, which resolves its path through `CommandLine::lookupResource`, i.e. the bridge, before any `Simulation` is bound; whoever revives it should pass `lookup_resource(path)` from the parsed options instead. Candidate: delete it, or fix it in M3/M9.

- **F45** (design, found D4b): `model/Host/WithinHost/Infection/DescriptiveIPTInfection.{h,cpp}` are not in `Model_CPP`, so they are never compiled; they use APIs that no longer exist (e.g. `initParameters` from `scnXml::IPTDescription`) and were left out of D4b's refactor, rename and modernisation. Their only hook in the compiled code is the no-op virtual `DescriptiveInfection::ipt_attenuate_asexual_density`. Other code in the directory with no caller: `EmpiricalInfection::set_patent_growth_rate_multiplier` and `EmpiricalInfectionParams::override_inflation_factors` ("only for parameterisation?"). Candidate: delete them (the IPT files with the virtual hook), with the user's agreement.
- **F46** (bug, found D4b): `util/rename_module.py` renames a member's declaration but none of its uses when one use is in a macro body (`#define L _laggedLogDensities` in `EmpiricalInfection.cpp`): clang-tidy drops the fix-its at the uses, the member-prefix pass still renames the declaration, and the token check passes because the declaration change is a planned rename. The post-apply "old names still used" list does show every missed use, and the build fails, so it cannot slip through silently. D4b used `--skip` and renamed the member by hand with the macro's removal. Candidate fix: treat a symbol whose uses clang-tidy reports without fix-its as `NO FIX-IT` in the plan, before applying.
- **F47** (design, found D4c): `WHVivax` has two members that are written to and read from checkpoints but never used: `p_event` and `p_first_relapse_event` (set to NaN in the constructor). `update()` computes the event probabilities in locals, one of which shadows `p_first_relapse_event`. A third, `pSecondRelapseEvent`, was neither used nor checkpointed and was removed in D4c's hand commit. Removing the other two changes the checkpoint format; candidate for H3.
- **F48** (surprise, found D4c): `WHVivax`'s `noPQ` heterogeneity is drawn once, in each host's constructor, from the health system's `pHumanCannotReceive`, which `changeHS` may not change ("changeHS cannot change pHumanCannotReceive value"). A scenario with no `liverStageDrug` element in its initial health system sets the value to 0, so a later `changeHS` that adds one with a non-zero `pHumanCannotReceive` fails at that deployment, not at startup (checked in D4c's A/B runs). Changes would need a decision on what existing hosts get; record only.
- **F51** (bug, found D4d): `--print-genotypes` crashes when a `parasiteGenetics` locus has a single allele. `print_genotypes` (`Genotypes.cpp`, before D4d `Genotypes::init`) sizes its code-to-name table by the number of genotypes (`cum_initial_freqs.size()`) but indexes it by allele code. Allele codes count every allele of every locus, genotypes are their product, so a locus with one allele next to one with two gives 3 codes and 2 genotypes. Checked in D4d with a locus `first` (one allele) before `mdr` and a locus `solo` after it: the base build d386e12f exits 139 (segfault) and the Debug build stops on `assert(code < allele_names.size())`. Without `--print-genotypes` the scenario is not affected. Fix candidate: size the table by the number of allele codes; changes stdout (from a crash to a table), so ask first.
- **F52** (surprise, found D4d): the `--print-genotypes` table is misaligned. The header writes `|` before each locus column, but each row writes `|` before and after it, so rows read `|       0|sensitive||present|    0.350|  1.000|` against a header `|Genotype|      mdr|   hrp2|init freq|fitness|`. Stdout only; fixing it changes output.
- **F53** (design, found D4d): diagnostics are looked up once and held by address in static or long-lived places: `NeonatalMortality`'s file-static `neonatalDiagnostic`, the `CMDTDiagnostic` decision-tree nodes (owned by a static tree cache) and the intervention components' `diagnostic` references. Since D4d they point into the `DiagnosticRegistry` that `Simulation` owns, so after the `Simulation` is destroyed they dangle. Nothing reads them then while one simulation runs per process; D6 (clinical, neonatal) and D8 (interventions) must move them with their owners before G-two-sims (D9). **D6b:** the neonatal one is settled: `NeonatalMortality` is a `Simulation` member declared after the `DiagnosticRegistry` and looks its diagnostic up there (66fdf1e1), so it no longer outlives it. The decision-tree nodes (D6c) and intervention components (D8) remain.
- **F54** (bug, found D5): a checkpoint's drug indices are not checked. `LSTMModel::checkpoint(istream&)` reads each drug's type index and passes it to `DrugRegistry::create_instance` (before D5 `LSTMDrugType::create_instance`), which indexes the drug-type vector with `[]`, so a corrupt or mismatched checkpoint (e.g. resumed with a scenario that lists fewer drugs) reads past the end instead of raising `checkpoint_error`. A bounds check would change only the failure, but it is an error path: ask before fixing (H3 rewrites checkpoint loading anyway).
- **F55** (surprise, found D5): PK/PD init messages. A drug listed twice (`Drug added twice: CQ`) is raised with `TRACED_EXCEPTION_DEFAULT`, so the user sees "Code error … This is likely an error in the C++ code. Please report!" and exit 65 for an input error (compare F3). Two messages have typos: "phenotype restrictions toorestrictive" (missing space, `LSTMDrugType.cpp`) and "when compartment2 or  conversion parameters" (double space). Fixing changes stderr; record only, ask the user (e.g. with M3).
- **F56** (bug, found D5): resuming from a checkpoint does not reproduce an uninterrupted run for some PK/PD drugs, on the base build too (78d96f4c). Three values are not checkpointed: (1) `LSTMDrug::vol_dist`, each drug instance's sampled volume of distribution, so on load it is re-sampled from the throwaway `LocalRng(0, 0)` that `LSTMModel::checkpoint` uses; this matters whenever `vol_dist` has a CV (shown by adding `CV="0.2"` to scenarioBSV's PPQ: its resume then diverges); (2) `LSTMDrugConversion::vol_dist_metabolite` and `last_bm` (the latter is 0 after load until the first concentration update, and the concentration getters divide by it); (3) `CommonInfection::kn`, each infection's cached IC50^slope per drug, which is re-drawn after resume, and the conversion model's `set_killing_parameters` draws two normals from the human's RNG to do so, shifting its stream. A diagnostic patch checkpointing (1) and (2) made scenarioPkPdModels resume exactly, but an AS-only variant still diverged through (3). No checkpointed ctest scenario has these (scenarioBSV's volumes have no CV, and no ctest scenario used the conversion model before D5), so G-exact never saw it. Fixing changes the checkpoint format and resumed outputs. **The user decided (2026-10-22): fix it in H3**, with the versioned checkpoint format; then move scenarioPkPdModels from `OM_BOXTEST_NC_NAMES` to `OM_BOXTEST_NAMES`. Until then it is registered without `--checkpoint-stop`.
- **F58** (bug, found D6a): `util/style.sh modernize` applies `cppcoreguidelines-prefer-member-initializer` without regard to the order of the reads it moves. It moves an assignment from a constructor body into the initializer list, i.e. ahead of the statements that preceded it in the body. When the moved expression can throw, that changes which error a bad scenario reports: `Parameters::operator[]` throws for a parameter the scenario does not describe, and in D6a the fix moved the `YStarSq` and `YStar1` reads of `PyrogenParams` ahead of `YStarHalfLife` and `Alpha`. Nothing in ctest saw it; the A/B variants dropping consecutive pairs of parameters do (`pathogenesis/pyrogen_no_params_25_13` and `_14_26` differ under a plant of the tool's order). D6a reverted the tool output and restructured the constructor first (aa825247). The earlier tool commits with this check (M2 a0f1112c, D2 0808f323, D4d e67dbef9) were checked: they moved constants, generated getters of required elements or a first statement, none of which can throw or was reordered past one that can. The modernize-module skill now says to look for this in the dry run. Candidate tool fix: report, rather than apply, a `prefer-member-initializer` fix whose moved expression calls a function, unless it was the body's first statement.
- **F65** (surprise, found B6): several expected outputs contain NaN, and the printed sign of a NaN depends on the platform. `outputModelNameModelOptionOverrides.txt` has measure 36 (simulated EIR) = `nan` at 19 surveys (from 504). `ctsoutSimpleMPDTest.txt` has three columns that are `nan` on every row: the 2nd, 4th and 15th. The header's 15 labels would name these `timestep`, `simulated EIR` and `res req(gambiae_ss)`, so the labels and values may be misaligned. `ctsoutGenotypes.txt` and `ctsoutNoMPDLarviciding.txt` print `-nan`. With `-ffp-contract=off` all numbers agree across macOS arm64, Linux arm64 and Linux x86-64 (b6-diag run 39879605135), but Linux x86-64 prints `-nan` where the others print `nan` in the first two files: SSE's default NaN has its sign bit set. `compareOutput.py` treats both as equal, so CI (tolerant, by the user's choice in B6) passes. A strict CI check on x86-64 would need the output writers to print every NaN the same way. The NaNs themselves (0/0 in an EIR or resource ratio?) are not investigated.
- **F66** (surprise, found B6): `test/scenario12a.xml` and `test/expected/output12a.txt` exist (since upstream 5cdd13e2), but `12a` is not in `OM_BOXTEST_NAMES`, so no test runs it and nothing checks that the expected file is current.
- **F67** (surprise, found B6): `build.sh` runs `export PATH=/usr/bin:$PATH` unconditionally (added for Cygwin in 26afd745). On macOS and Linux this puts the system tools ahead of everything else on PATH, so CMake picks `/usr/bin/python3` (3.9 on the macOS runners) over a newer Python from setup-python, Homebrew or a venv. The same goes for any other tool CMake looks up by name, such as `cmake` or `clang` from Homebrew. B6 works around it in CI with `CMAKE_PROGRAM_PATH`, which `find_program` searches before PATH. A fix would make the export Cygwin-only, but that changes which tools `build.sh` picks for every user.

## Closed

- **F61** (bug, found after D6b; fixed B6): the macOS CI jobs failed every statistical test and `stats_tool_check_scenario` (52 of 105 at 4db10096, 52 of 110 at 7d115055) with `TypeError: zip() takes no keyword arguments`: `test/stats` uses `zip(strict=True)` (Python 3.10+), and CMake found the runners' `/usr/bin/python3` (3.9.6). Fixed in 89fd11f7 and 773f2154. `test/CMakeLists.txt` registers `stat_*`, `statfull_*` and `stats_tool_check_scenario` only when the interpreter is 3.10 or newer, and otherwise says why (`stats_tool_generate_reference` runs through `uv` and is unaffected). The build workflow sets up Python 3.12 and points `CMAKE_PROGRAM_PATH` at it, because `build.sh` puts `/usr/bin` first on PATH (F67). Since run 39882681731 the macOS jobs run all 110 tests.
- **F62** (surprise, found after D6b; fixed B6): the Linux CI jobs' LifeNet1/2 outputs (and EffectiveDrug on arm64) differed from `test/expected/` by more than 1e-6. The cause is FMA contraction, not the maths library. CMake builds with `-std=gnu++20`, under which GCC fuses across statements (`-ffp-contract=fast`); that matters on arm64, while x86-64 without `-march` has no FMA, and Apple clang fuses within an expression (`on`). The b6-diag run 39879605135 (macos-15, ubuntu-24.04, ubuntu-24.04-arm, each with default flags and with `-ffp-contract=off`) shows that with contraction off all three give the same numbers for all 56 scenarios (x86-64 prints two NaNs as `-nan`, F65). On macOS, contraction off moves only LifeNet1/2 (measure 36, simulated EIR, the last printed digit). The user chose (2026-10-23) to compile with `-ffp-contract=off` on GCC and Clang (d29f4df8) and to regenerate LifeNet1/2's expected outputs (b3bf778f). The bit-for-bit comparison with GSL's polar-method normals now allows 1e-12 (fd5a52bd), because Homebrew's GSL is compiled with contraction. The user kept CI's tolerant binary-mode check.
- **F63** (bug, found after D6b; settled B6): the ubuntu-22.04 CI job failed at configure (CMake 3.22 < 3.24), and its GCC 11 has no `<format>`. The user chose (2026-10-23) to drop the job (b4f516a1).
- **F64** (surprise, found after D6b; fixed B6): the Style job reported `cppcoreguidelines-slicing` at `LSTMDrugType.cpp` (`string(name.get())`) on Ubuntu's xsdcxx 4.0 headers, which the local xsd 4.2 headers do not trigger. Fixed in 523adf7b by copying through a `const std::string&`. Style run 39879164982 at 7d115055 showed this as the only site. G-style results can still depend on the `xsd` version: a new copy of a generated string type into a `std::string` passes locally and fails in CI.
- **F59** (bug, found D6b): a `changeHS` cannot change the event scheduler's `dailyPrImmUCTS`. `EventSchedulerParams::set_parameters` (before D6b `ClinicalEventScheduler::setParameters`) appends the cumulative probabilities to `cum_daily_pr_imm_ucts` on every health-system load without clearing it, so after a `changeHS` the vector holds the initial values followed by the new ones. The treatment-seeking delay is drawn by scanning from the start, and the initial values end in 1.0, so the new ones are never reached. Shown in D6b's A/B runs: ESTS with a `changeHS` that sets `dailyPrImmUCTS` to 0.2, 0.8 gives outputs byte-identical to one that keeps 1 (`clinical/es_changehs_daily_pr` vs `es_changehs_same`), while one that changes `uncomplicatedCaseDuration` moves them (`es_changehs_case_duration`). The other values `set_parameters` reads are assigned, so they do change. No ctest scenario is affected by a fix: the two event-scheduler scenarios with a `changeHS` (EffectiveDrug, Molineaux) keep `dailyPrImmUCTS` at 1. **Fixed in 41c35aa4** (the user's decision, 2026-10-22): the vector is cleared before it is filled. Only the two A/B variants that change `dailyPrImmUCTS` in a `changeHS` moved (nUncomp 541 → 597); G-exact unchanged. Catch2 test `[clinical][F59]` in `unittest/ClinicalTests.cpp`, and a scenario test, scenarioESChangeHS (f8f0896b), whose output before the fix was byte-identical to scenarioESTS's.
- **F60** (bug, found D6b): `ClinicalModel::latest_state` (before D6b `latestState`) is not initialised by the constructor; it is set at each human's clinical update. The `DecisionTreeComponent` intervention passes it to its tree (`get_latest_state()`), and a timed or continuous deployment can reach a human born in the previous step's `population.update()` before that human's first clinical update, so the tree reads an indeterminate value (undefined behaviour). It matters only for trees whose nodes test the state (`<uncomplicated>`, `<severe>`). D6b kept it as it was (NOLINT on the constructor, 51663e3e), since initialising it (e.g. to `Episode::None`) could change outputs in that case; no ctest scenario or A/B variant showed a difference either way. **Fixed in 75700eda** (the user's decision, 2026-10-22): it starts at `Episode::None`. The A/B variant `clinical/dt_intervention_severe_node` (e169341c) deploys a `<severe>`-node tree to every newborn before its first update; its outputs move when the value starts at `Complicated` but are identical for the base build and the fix, as is every other variant and ctest scenario, so on this platform the old read never saw anything that mattered. Catch2 tests `[clinical][F60]` construct each model in storage filled with 0xA5 and fail without the fix.
- **F57** (bug, found and fixed D5): `test/CMakeLists.txt` registered the scenarios in `OM_BOXTEST_NC_NAMES` (tests with broken checkpointing) as `run.py [args] -- NAME`, so `NAME` was passed to openMalaria and, with no scenario named, `run.py` would have run all of them. The list had been empty since before this branch. Fixed in 89c90989, before scenarioPkPdModels became its first entry.
- **F50** (bug, found and fixed D4d): `util/modernize_module.py` ran clang-tidy on the Release compile database without `-UNDEBUG`, so `assert(...)` bodies were not parsed (F23's gap, which F23 thought harmless for this tool). In D4d, `modernize-loop-convert` turned iterator loops in `Genotypes.cpp` into range-for loops while an `assert` in the body still used the old iterator (`i->alleles`, `*a`). - **F31** (design, found S6): the statistical check has little power against small, real changes. A 20% higher force of infection moves the mean prevalence by 1.9–2.5 single-run SDs in ten scenarios, yet the default rerun rule detects it with ≥ 80% power in only 2 of 44 scenarios (Genotypes, Penny), and `--replicates 20` in 10. The reason is structural: each run is judged against intervals that hold 99% of single runs, and `--replicates` counts failing runs rather than testing where the K runs lie as a group. A test of the K-run mean of each aggregate against the reference mean and SD would see a 1-SD shift at K = 20 as z ≈ 4.5. Matters for D2b/M4/M8, whose only gate is G-stat: a pass there means no large change, not equivalence. Details in `test/stats/README.md`. **Settled in S7** (bf62b4ff, 190ffc99, 9e1f093e, fb09fd66, 5cdcf528): `--replicates` is now a group test of the 20-run mean of every aggregate and survey measure total, with a leave-20-out threshold at α = 0.01% per scenario, run by `ctest -C full -L statistical-full`. On the kept S6 runs it has ≥ 80% power against a 20% higher force of infection in 24 of 44 scenarios (was 10), and no false failure in 438 fresh groups.
